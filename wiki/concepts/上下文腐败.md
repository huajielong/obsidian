## 定义

上下文腐败（Context Corruption）是指 **LLM 在上下文窗口已填充内容超过一定阈值后，模型效率与输出质量突然显著下降的现象**。这不是一个"缓慢衰减"的过程，而是在一个临界点附近发生的急剧性能崩塌。

## 核心机制

- **触发阈值**：在上下文窗口填充到约 50-60% 时触发性能衰减——以 Claude Code 的 200k token 窗口为例，大约在 100k-120k tokens 时出现问题
- **阈值不随窗口扩大而移动**：无论上下文窗口是 200k、1M 还是 2M tokens，腐败的触发点大致停留在约 100k-120k tokens 附近。单纯扩大窗口不能解决腐败问题
- **突然性**：效率下降不是渐进式的，而是在到达临界点后突然发生

## 上下文窗口组成

在实际使用中，每一轮交互都会消耗上下文 token：

- 系统提示（System Prompt）
- 系统工具定义（System Tools）
- 技能文件（Skills）
- MCP 工具描述
- 记忆文件（Memory）
- 消息历史（对话轮次）
- 文件内容（读取的文件）

## 管理策略

### 1. 主动重置窗口
- 使用 `/clear` 命令清除当前对话上下文，开启全新会话
- 这是最直接、最可靠的方案
- 建议在上下文使用量接近 50% 时主动执行

### 2. 谨慎使用 /compact
- `/compact` 命令会自动总结对话内容并开启新会话
- **缺点**：模型可能选错重点，将重要信息遗漏在压缩过程中
- **推荐做法**：如果必须保留关键上下文，手动让 Claude Code 按你的要求总结，然后手动复制粘贴到新会话

### 3. 实时监控
- 创建常驻状态栏（HUD）或状态栏插件，实时显示上下文窗口使用量
- 在接近 50-60% 阈值时主动采取行动
- 可通过 `/context` 命令随时查看当前状态

### 4. 精简上下文策略
- 优先使用少量"事例"（Concrete Examples）而非冗长的指令说明
- 控制 CLAUDE.md 和 AGENT.md 文件的大小，只包含真正必要的规范
- 了解"少即是多"原则——不必要的上下文文件反而会降低模型表现

## 实验证据（李宏毅《生成式AI导论2025》第2讲）

李宏毅课程用一个**"复制任务"实验**直接演示 Context Rot（他把 "rot" 译为"腐烂"）：

- **实验设计**：给模型一串文字（Apple Apple Apple…中间混入 Apples 再变回 Apple），要求**原样复述**。Gemini / Qwen / GPT-4 Turbo / Claude 等号称超长窗口的模型，在输入约 **10^4（一万）token** 时复制正确率就急剧下降——而 Gemini 声称可输入 200 万 token，**远未到达窗口上限，模型就已开始困惑**。
- **Lost in the Middle（迷失在中间）**：RAG 给 20 篇文章（约 4000 token），正确答案出现在 context 最前/最后时答对率高，**出现在中间时最容易答错**——甚至低于完全不 RAG、凭模型自身知识回答。模型（和人类记忆一样）更记得长 context 的开头与结尾。
- **Databricks 实验（资料越多，正确率先升后降）**：RAG 检索放进 context 的 token 越多，多数模型正确率先升后降；Meta 405B **给最多资料时正确率还不如给最少资料**。
- **挤牙膏式提问伤害能力**：把同一任务拆成多步、分次给需求（每次只给一部分），模型的 **Capability（答对率）下降、Unreliability（答对/答错题差距）上升**——一次把需求讲清楚反而更好。对应课程名句：**Context Engineering = 把需要的放进去、把不需要的请出来**。

## 研究支持

2026 年研究表明，像 CLAUDE.md 和 AGENT.md 这类上下文文件在某些情况下对编码助手有负面影响——相比完全不提供任何代码库上下文，它们可能 **拉低任务成功率**，同时让 **推理成本飙升超过 20%**。这进一步印证了上下文腐败的严重性和精简上下文策略的必要性。

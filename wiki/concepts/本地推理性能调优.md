## 定义

本地推理性能调优是在有限显存/内存条件下，通过后端选择、模型路由、权重量化、KV cache 量化、上下文长度、MoE 卸载与投机解码等手段，最大化本地 LLM 吞吐并避免 OOM 的系统方法。其目标不是“跑最大模型”，而是“用对的模型、以可接受的延迟稳定运行”。

## 关键信息

### 第一原则：后端选择

- 同一 GGUF 模型，llama.cpp 通常显著快于 Ollama 0.40.x（本机 Qwen3.6：65 vs 6.6 tok/s；Gemma 4：34 vs 5.3 tok/s）
- 原因：Ollama 对新架构不支持 MoE 专家卸载，只能整层卸载到 CPU；llama.cpp 支持 `--n-cpu-moe`、MTP 投机解码、KV cache 量化等细粒度控制
- 结论：大模型优先 llama.cpp；Ollama 用于模型管理、翻译和小模型

### 第二原则：任务路由

| 任务 | 模型档位 | 理由 |
|------|----------|------|
| 编程 / Agent / 复杂推理 | 35B MoE（Qwen3.6-35B-A3B） | 需要工具调用与长上下文 |
| 快速问答 / 图片 / 视频帧 | 12B 多模态（Gemma 4 12B） | 速度与显存更优 |
| 中英翻译 | 4B 专用（TranslateGemma） | 专用模型 78 tok/s，远快于 35B |
| 显存不足时的翻译 | 4B CPU 版 | 0 显存，22 tok/s |

### 第三原则：量化三层

1. **权重量化**：Q4_K_M 是 12GB 显存的甜点；Q8 放不下，Q2/IQ2 损害工具调用可靠性
2. **KV cache 量化**：q8_0 几乎无损；q4_0 更省显存但轻微损失；f16 最占显存
3. **思考模式**：thinking 会显著增加 token 与时间；不需要时关闭（Ollama `--think=false`；llama.cpp `--reasoning-budget 0`）

### 关键参数（llama.cpp）

| 参数 | 作用 | 调优方向 |
|------|------|----------|
| `--n-cpu-moe N` | MoE 专家卸载层数 | 调小更快更吃显存；调大更省显存更慢 |
| `-ngl 999` | 全部层上 GPU | 保持 |
| `-c N` | 上下文长度 | 按任务开：翻译 2K，日常 8–16K，编程 32K |
| `-fa on` | Flash Attention | 保持 |
| `-ctk/-ctv q8_0` | KV cache 量化 | 保持 |
| `--spec-type draft-mtp` | MTP 投机解码 | 保持，本机提升约 42% |
| `--reasoning-budget 0` | 关闭思考 | 翻译/快速问答开启 |
| `--parallel 1` | 单用户 | 保持，省内存 |

### 显存预算方法

1. 先测单模型显存占用（`nvidia-smi` / `ollama ps`）
2. 列出常驻后台程序（TTS、浏览器、录屏、NVIDIA Broadcast）的显存
3. 组合不超过总显存，预留 0.5–1GB
4. 本机 12GB 的关键边界：Index-tts2（约 8GB）不能与 Qwen/Gemma 同时跑；TTS + 翻译时翻译走 CPU

### 调优流程

1. 先保证能加载、不 OOM
2. 每次只改一个参数，重启，测同一段输入
3. 观察 `nvidia-smi` 与 llama-server 输出的 tok/s
4. 目标：显存留 0.5–1GB 余量，速度稳定
5. 优先级：调 `--n-cpu-moe` → 降上下文 → 关后台程序 → 换更小模型

### 常见误区

- 只用“最大模型”：翻译用 35B 反而慢且占显存
- 同时跑两个 llama-server：12GB 显存放不下
- 把 Q4 模型“升级”成 Q6 恢复质量：权重量化固定在模型文件里，做不到
- 忽视 prompt 处理速度：Claude Code 系统提示约 20K token，prompt tok/s 比生成 tok/s 更影响首响应

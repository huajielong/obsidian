## 核心摘要

李宏毅《生成式人工智慧與機器學習導論2025》第二讲"上下文工程 (Context Engineering) — AI Agent 背后的关键技术"，围绕 **Context Engineering（上下文工程）** 展开：它把语言模型看作函数 `f`，训练是改 `f`（改不了，因为线上模型都是闭源的），**Context Engineering 就是改输入 x**——自动化地帮 `f` 准备合适的输入，让接龙结果符合预期。课程的核心论点一句话概括：**Context Engineering 的核心目标就是"避免塞爆 context"**——把需要的东西放进去、把不需要的东西清出来，而在 AI Agent 时代，这个任务变得尤其关键，因为 Agent 循环（观察→行动→环境反馈→新观察）本质仍是文字接龙，却会快速消耗有限的上下文窗口。

课程先讲一个**完整的 Context 应该包含什么**：User Prompt（任务+详细指引+前提+范例）、System Prompt（开发者预设的身份/日期/限制/风格）、对话历史（短期记忆）、长期记忆（2024 年 9 月后 ChatGPT 的"记忆"）、搜索引擎/RAG 结果、工具调用结果、以及模型自己产生的 reasoning（"脑内小剧场"）——这些都是"塞进窗口"的候选。随后用三个方向的实验证据说明**为什么"能输入百万 token"不等于"能读懂百万 token"**：Databricks 发现 RAG 资料越多正确率先升后降（Meta 405B 资料最多时还不如最少）；"Lost in the Middle"实验显示正确答案在长 context 中间时，模型答对率甚至低于不做 RAG；"Context Rot（上下文腐败）"实验显示复制 Apple/Apples 这类简单任务，在远未达到窗口上限（约 10^4 token）时模型正确率就急剧崩塌，且"挤牙膏式"分步提问会显著拉低模型能力与稳定性。

课程最后给出 Context Engineering 的**三大常用招数**：① **选择（Selection）**——RAG、LLM 帮选关键词、Reranking、Provence 句子级筛选（<300M 参数小模型）、工具版 RAG（工具太多只挑相关的）、记忆挑选（史丹佛小镇 recency/importance/relevance 三指标；SpringBench 证明负面例子反而有害）；② **压缩（Compression）**——递归式摘要（每 N 回合/90% 满/定时触发），摘要细节存入硬盘日后用 RAG 取回，摘要中留"指针"避免 RAG 检索错误；③ **Multi-Agent**——从 Context Engineering 角度看，多智能体本质是**隔离各自的 context**（总召 agent 只记"餐厅订好了"一句话，不装订位细节），让每个窗口只装有限的、相关度最高的信息。

## 一、Context Engineering 与 Prompt Engineering：新瓶装旧酒，但关注点不同

### 1. 语言模型 = 函数 f：改 f（训练）还是改 x（输入）？

- 语言模型就是文字接龙：给定输入 Prompt（x），预测下一个 Token（f(x)）。
- 输出不对时，要么**改 f**（训练 / Learning——改变参数），要么**改 x**（输入）。
- 关键现实：今天的模型**大多是线上闭源模型，f 你根本改不了**；所以唯一可做的就是**把输入 x 准备合适**——这正是本课主旨。
- 课堂上"没有任何模型被训练，唯一被训练的是人类"。

### 2. Context Engineering 与 Prompt Engineering 的关系

- **本质相同**：都是"把语言模型的输入弄好，让它得到要的输出"。李宏毅的直白观点：Context Engineering 就是把 Prompt Engineering **换个更潮的名字**（如同 Neural Network → Deep Learning 的新瓶装旧酒），两者指涉同一概念，**关注重点不同**。
  - 旧 Prompt Engineering 关注：**特定格式**（JSON、井字号分节）与**神奇咒语**——但随着模型变强，格式已没那么重要（人看得懂模型就看得懂），神奇咒语也失效了。
  - 新 Context Engineering 关注：**自动化管理语言模型的输入**（用模型自己管自己的输入），尤其面向 AI Agent 场景。
- 为讲解方便，本课**把 Context 与 Prompt 划等号**（Context 即语言模型的输入）。

### 3. 神奇咒语（Magical Incantation）时代的遗迹

- **GPT-3 时代**（ChatGPT 前身，几乎不可用）：输入输出关系荒谬，靠咒语操控。
  - 例子：要求"回答越长越好"→ 平均 18.6 字 → 23.76 字；但加一串"位置"字样，反而暴涨到 **34.3 字**（出自李宏毅实验室论文）。
- 经典咒语：`Let's think step by step`（模型能力起飞）、"请确保答案正确"、"先深呼吸再回答"、"这题对我非常重要"、"答对给你小费"——都曾提升正确率。
- **"小费/奖励"实验**（测 ChatGPT 最喜欢什么）：要求用恰好 200 字写故事。结果它最喜欢"达成世界和平"，最不在意"母亲为你骄傲"（因为它没有母亲）。
- **咒语效力随时间衰减**（关键趋势）：同一数学应用题，2023-06 GPT-3.5 无咒语 72% / 有咒语（一步一步思考）88%；到 2024-02 无咒语已到 85% / 有咒语仅 89%。**模型本来就应该尽全力，不该靠咒语才思考。**

## 二、完整的 Context 应该包含什么

### 1. User Prompt：任务 + 详细指引 + 前提 + 范例

- **详细指引**：如写请假信，除了任务（跟老师请假），还要交代"先道歉→说明理由（身体不适，别提'不想上课'）→之后更新进度→50 字以内→语气严肃"等额外条件。
- **前提要讲清楚**：语言模型不会读心术。例："有人告诉我要用载具吗？" 没前提时模型答"交通工具或电子设备"；给出前提"在超商结账时店员的问话"→ 正确答"电子发票储存工具"。
  - 影像例子：曼谷运河照片里的动物。直接问 ChatGPT → "鳄鱼"；补充"现在在泰国曼谷"→ "水巨蜥"（泰国吉祥象征，代表偏财运）。**告知拍摄地点就能改变答案。**
- **范例（Examples）**：火星文改写。不给范例时 ChatGPT 自创"把字换成其他字"；给范例"要ㄑ冒险 ㄉ人来找我"后，它立刻正确地把"我们的环岛之旅"改成"我们ㄉ环岛之旅"。**清楚的例子能直接影响模型能力。**

### 2. System Prompt：开发者预设的固定输入

- System Prompt 是**平台开发者认为每次互动都需要的资讯**，用户不可见。
- **Claude 3 Opus 的 System Prompt 公开且超过 2500 字**，内容拆解：
  - 身份：你是 Claude，由 Anthropic 打造
  - 日期：今天是几月几号（模型做文字接龙不可能知道日期，全靠这里喂）
  - 使用说明与限制：API 怎么用、别教合成化学物质/核武器
  - 互动规范：用户不高兴就引导按倒赞；回应别以"好问题/Good Question"开头（文字接龙太容易接出它）
  - 知识截止：知识到 2025 年 1 月，之后的问"我不知道"
  - 定位：别说自己是人类、别说自己有意识；**被纠正时不要马上承认错误**（模型太容易附和人类，要仔细思考后再回应）

### 3. 对话历史 = 短期记忆

- 例子：先教它"隔壁老王姓法，叫法老王"，同对话内再问"隔壁老王是谁"→ 答"法老王，天下无敌王"。它只是**根据前面一长串历史继续接龙**。
- **误解澄清**：跟模型对话**无法改变它的参数**——开新对话它就忘光（"法老王"变回"常见的幽默角色"）。
- **2024 年 9 月后 ChatGPT 有了长期记忆**：在"自定义 ChatGPT → 记忆"开启。长期记忆被植入在你看不到的问题前面；OpenAI 营销活动教大家问"我是什么样的人"来展示记忆。课程结尾会讲模型处理记忆的方法，可对照猜测 ChatGPT 的实现。

### 4. 外部资讯：搜索引擎 / RAG

- 模型知识有限且过时 → 先把问题丢到搜索引擎或自己的数据库，搜到额外资讯再让模型接龙 → **RAG（Retrieval-Augmented Generation）**，作业二实现的技术。
- **RAG 不保证正确**：语言模型始终是文字接龙，给了最新资讯仍可能犯错。
  - 经典失败案例：Google AI Overview 测试期被问"起司黏不住在披萨上怎么办"，模型答"加 1/8 杯无毒胶水"（把 Reddit 玩笑当真）。
  - ChatGPT-4o 开搜索：能答对"台大专业学程联盟"的课程并给对网址，但会**凭空说"10 门课都是进阶课程"**（错误资讯）。

### 5. 工具使用结果（Tool Calling）

- 在 Context 里写好工具使用方式：通用工具说明 + 特定工具范例（如 `temperature(城市, 时间)`），用人类看得懂的文字即可，模型就能用。
- **关键机制**：模型输出 `<tool>temperature('高雄','时间')</tool>` 这**只是一串文字**，不会真的驱动工具。**需要开发者自己写小程式**（胶水脚本 / eval 循环）把 `<tool>` 内指令取出来真正执行，再把输出放回 `<tool_output>`，让模型继续接龙。
- 工具调用过程与中间结果可对用户完全隐藏——用户只看到最终答案，误以为模型文字接龙"算出了气温"。
- **实操（Gemma 2 9B + Colab）**：见下方"五、工具调用实操"。

### 6. 模型自己产生的思考过程（Reasoning / 脑内小剧场）

- 现在很多模型号称"深度思考"（GPT 的 O 系列、DeepMind 的 R 系列、Gemini 家族）：先不直接给答案，先在"脑内小剧场"把各种解法演练一遍（A 解法→验算不对；B 解法→好像对；C 解法→不好），再据此给出最终答案。
- 脑内小剧场**对用户可选择不看甚至根本不能看**（ChatGPT 只给摘要）。
- **这些思考过程也是 context 的一部分**——只是不是人外加的，而是模型自己放进去的；模型根据自己产生的 context 再做文字接龙。深度思考模型怎么练成的见课程延伸影片。

### 小结：Context Engineering 的核心目标

> **避免塞爆 context**：想方设法只放需要的东西进 context，清理掉不需要的内容。

## 三、为什么 AI Agent 时代尤其需要 Context Engineering

### 1. 从一问一答到 Agentic Workflow 到 AI Agent

| 阶段 | 定义 | 例子 |
|------|------|------|
| **一问一答** | 问问题→接龙出答案 | 传统聊天 |
| **Agentic Workflow** | 人类给模型订一个 **SOP**，按步骤执行 | 批改作业：①先检查是不是真作业（防 Prompt Injection）→②给分数→③验证分数是否合理 |
| **AI Agent** | 模型**自己决定解题步骤**，并根据环境变化**灵活调整计划** | 研究问题：上网收集资料→形成假设→写程式做实验→验证→不成立再收集资料→循环→写报告 |

### 2. Agent 的运作循环（Observation → Action → Environment）

```
人类给目标 → 模型看当前 Observation → 采取 Action（调工具/写程式/输出报告/联系人类）
   → 环境（人类、工具等模型以外的一切）改变 → 产生新的 Observation → 循环
```

- 从模型角度看，Agent **始终只是在做文字接龙**：根据 obs1 产生 action1，根据 obs1+action1+obs2 产生 action2……与对话没有本质区别。它靠"很会接龙"做长时间运行、完成更复杂任务。
- **AI Agent 相较传统 Agent（如 AlphaGo）的优势**：输出近乎无限可能（AlphaGo 只能落子）；可以用人类语言下达指令与反馈（AlphaGo 听不懂人话）。
- **演示**：
  - **ChatGPT Agent Mode**（云端电脑）：让它订高铁票（9/20 上午 9-10 点台北→左营 2 张），它会开屏幕画面、自己搜高铁网站、点台北/左营/2 张/设日期（中间点错 19 再修正），最终"不肯输入验证码"停下——当前仍不完善，但威力无穷。
  - **Gemini CLI**（免费，背后可免费动用 Gemini 1.5 Pro）：真的会碰触你的电脑——演示让它关掉投影片（真的关了）、删档案（它愿意删）、做一个贪食蛇游戏（多步骤：做计划→征求同意→建文件夹→生成 index.html/style.css/script.js→玩家说"太快了"→它改 100→150 调速）。它会告诉你 context 用了多少（演示时仅用 1%）。

### 3. 挑战：能输入百万 token ≠ 能读懂百万 token

- **Context Window 不断变大**：GPT-4 约 3 万 token → Claude 系列 10 万 → Gemini 100 万 → Llama 4 号称 1000 万；Gemini 1.5 号称 200 万 token（≈ 哈利波特全集 + 几乎 3 本魔戒）。
- **但"能输入"不等于"能读懂"**：就像翻完哈利波特全集不一定记得全部内容。**在远未到达窗口上限时，模型就已经对输入感到困惑。**
- **证据一：Databricks 博客 —— RAG 资料越多，正确率先升后降**
  - 横轴=放进 context 的搜索 token 数，纵轴=回答正确率。资料少时资料越多越好（越可能含答案）；资料太多模型"看不下"。
  - 绿色线（Meta 405B）：**给最多资料时正确率还不如给最少资料**。
- **证据二：Lost in the Middle**
  - RAG 给 20 篇文章（约 4000 token，GPT-3.5 时代），正确答案出现在最前/最后时答对率高；**出现在中间时最容易答错**——甚至低于"完全不 RAG、凭模型自身知识回答"的红色虚线。
  - 模型（和人类记忆一样）比较记得长 context 的开头与结尾。
- **证据三：Context Rot（上下文腐败 / 腐坏的上下文）**
  - 简单任务：复制一段文字（Apple Apple…Apples…Apple）。各号称超长窗口的模型（Gemini/Qwen/GPT-4 Turbo/Claude）在输入到约 10^4 token 时，**复制正确率就急剧下降**——而 10^4 离 Gemini 的 200 万上限非常遥远。
  - **挤牙膏式提问伤害能力**：把同一任务拆成多步、分次给需求（每次给一部分），模型的 **Capability（答对率）下降、Unreliability（正确/错误题差距）上升**——一次把需求讲清楚反而更好。
- **结论**：Context Engineering 就两句话——**① 把需要的东西放进去；② 把不需要的东西清出来，保持 context 整洁**，且这两步往往也靠 AI（语言模型）辅助完成。

## 四、三大常用招数

### 招数 1：选择（Selection）——别什么都往 context 里塞

- **RAG 就是"选择"的典型**：不可能把整个互联网塞进去，先经搜索引擎只搜出与任务相关的资料。RAG 本身是 Context Engineering 的核心技术。
- **RAG 框架内的加强版**：
  - **LLM 帮选关键词**：把用户 Prompt 转成搜索关键词（模型帮你想该搜什么）。
  - **Reranking（重排序）**：搜索引擎给一大堆文章，不一定每篇相关——用模型再挑一次，只留最相关的进 context。
  - **Provence（近文）**：不止选文章，**选"句子"**。用一个参数不到 300M 的极小模型（2018 年看是庞然大物、今天是很小的模型），唯一任务就是判断"某句话跟当前 Prompt 有没有关系"，把文章进一步缩短，避免塞爆 context。
- **工具版 RAG（Tool Selection）**：有 1000 个工具不可能全读说明 → 把每个工具说明当作一篇文章，根据用户需求只搜出相关工具的说明进 context。**给模型太多工具它会发疯，"less is more"**——这也是 ChatGPT Plugin 当年"每次最多只能选 3 个"的原因（后来 Plugin 默默消失了）。
- **记忆挑选（Memory Selection / 对记忆做 RAG）**：
  - **史丹佛小鎮（Stanford Smallville，2023 年初）**：每个 AI（如 Isabella）的记忆太琐碎（"有一张桌子，啥事也没发生"×N），不能全塞 context，存在硬盘里，需要时用 RAG 搜出最相关的。三条打分指标：**recency（多近发生的）+ importance（进记忆时自评多重要，如"有人告白"=9、"有张床"=0）+ relevance（与当前问题多相关）**，按总分排序只取最重要的进 context。
  - **SpringBench（Appier，NeurIPS 去年）**：模型连续回答问题，每次从环境拿对/错反馈，期望越答越好。做法：按当前问题用 RAG 搜出最相关的过往例题进 context。结果：**每次挑不同范例 > 固定五个范例 > 无记忆**。**关键发现：给"过去答错的记忆"反而大幅损害能力（负面例子不只没用还有害）**——如同"不要想白熊"反而更容易想到白熊；但把错误经验放进 context 又不被反噬，是未来可研究的问题。

### 招数 2：压缩（Compression）——context 太长的兜底

- Agent 互动越来越长，历史可能超过 context window。直接丢历史 → 完全失忆；**更好的做法是让一个专门做摘要/压缩的模型**读历史、抽出关键部分当长期记忆。
- **递归式多次压缩**：设定触发条件（每互动 100 回合 / context 90% 被塞满 / 固定时间）就压缩一次；第二次压缩包含第一次压缩的结果再压——**远古记忆随时间"随风雨消逝"**。
- **ChatGPT 两套记忆的猜测**：一套是显式"记住 X"（写在可后台查看的笔记本，除非你改否则永不消失）；另一套是隐式、会随风消逝、你看不到（只能问"你记住了什么"）。隐式那套疑似用了递归压缩技术；且你只能口头请它"忘掉某事"，有时有用有时没用。
- **为什么压缩有用**：Agent 与环境的互动（尤其 **Computer Use**）会产生大量本就该丢弃的琐碎内容——订餐厅时"滑鼠移到某位置→网页变了→弹出广告→按 XX 关掉"这一连串，对后续完全可浓缩成一句"A 餐厅订位成功，9/19 下午 6 点，10 人"。
- **怕摘要丢关键资讯？**
  1. **摘要前的完整内容放到可长期存储的空间**（硬盘近乎无限，context 有限），日后用 RAG 读回。
  2. **在摘要里留"指针"**：如"如果你想知道更详尽的内容，打开这个 .txt 档，里面有你那年夏天美好的回忆"——能打开文件系统的模型需要时就去打开，避免 RAG 检索错误。

### 招数 3：Multi-Agent —— 从 Context Engineering 角度隔离 context

- **ChatDev**（软件公司）：CEO（下指令）/ CTO / programmer / reviewer / tester 各司其职。有用角度一：每个 agent 有不同专长（会写程式当 programmer，只会嘴砲当 CEO）。
- **更有趣的角度二：multi-agent 是管理 context 的有效方法**。
  - 反例（单 agent）：一个"组织出游"agent 既要规划行程，又要用 Computer Use 订餐厅（跟餐厅网页一番互动）、订旅馆（再一番互动）——每个 agent 的 context window 都有限，大量 Computer Use 互动后 context 很快塞满，模型再也无法正确做事。
  - 正例（三 agent）：总召 agent 只跟人类互动、管大方向；订餐厅 agent 收到"去订餐厅"指令后跟网页互动、回一句"订好了"；总召 context 里只需记"餐厅订好了"一句话，继续接龙派第二个人去订旅馆。**每个 agent 的 context 只装有限的、与自己相关的资讯**——即使三者没有专长差异，隔离本身就有帮助（总召把订餐厅的 context 卸给另一个 agent，自己 context 更短、更高效）。
  - **overview paper（综述论文）例子**：单 agent 读上百篇论文会超过窗口上限；multi-agent 则**每篇论文由一个 agent 分读**（参数可完全相同），各写摘要，再汇总交给撰写 agent——不同的论文没必要放进同一个 context。这与人类社会分工类似。
- **LangChain 的 single vs multi 实验**：简单任务 single-agent 可能更好（所有 context 由一个 agent 主管，无信息孤岛）；**复杂任务 multi-agent 占巨大优势**（single-agent 吃不消）。multi-agent 也有组织病（订旅馆的不知道订了哪家餐厅，可能相隔很远）。

## 五、工具调用实操：Gemma 2 9B + eval 循环（Colab）

- 用 Hugging Face pipeline 加载 **Gemma 2 9B**，创建两个"工具"：`multiply(a,b)` 与 `divide(a,b)`（就是普通 Python 函数）。
- **核心教训：模型永远只能输出文字**。它输出 `multiply(3,4)` 只是一串文字，不发生任何效果。要真正执行，需要开发者调用 **`eval()`** 把这串文字当指令执行——`eval('multiply(3,4)')` 才得到 12。
- **第一次（没有 eval 循环）的失败演示**：只告诉模型可以用工具，它"自己接龙"出 `<tool>multiply</tool>`→工具输出 24642→`<tool>divide</tool>`→32.258。**实际上它一个工具都没调用（"只呼叫了一个寂寞"）**——111×222=24642 是它心算对的，24642÷777 心算出 32.258（正确答案 31.714，差 1 点多）。模型 hallucinate 出"工具输出"继续接龙。
- **正确做法（while 循环）**：
  1. 把 messages 丢给 pipeline → 得 response
  2. 若 response 含 `<tool>...</tool>`，**只撷取该指令**（其余 hallucinate 的部分丢掉）
  3. Python 里 `eval(command)` 真正执行 → 把结果包进 `<tool_output>...</tool_output>` 
  4. 把"工具指令+工具输出"塞回 messages（Gemma **没有独立的 tool role**，把工具输出当用户消息会被误判，所以必须用 `<tool_output>` 标记让模型认出这是工具输出）
  5. 循环直到输出不含 `<tool>` 标记 → 那才是最终答案
- **工具调用过程可隐藏**：用户只看到"111×222÷777=31.714"，以为模型文字接龙会算数。
- **模型不完全相信工具**：让假工具返回"高雄气温比太阳表面还高"，模型会质疑"你是不是输入有误"；问"你好吗"时模型自己决定不调用工具（没有对应工具）。说明模型只在需要时用工具，且对荒唐的工具输出有一定识别力。
- **Computer Use = 通用工具**：把"键盘/鼠标移动/点击"也当作工具，给一张屏幕截图 + 说明，模型就能决定下一步（演示：给 ChatGPT 截图问"订阅李宏毅 YouTube 频道下一步是什么"，GPT-4o 能答鼠标移到 (604,304) 点左键、键入"李宏毅 YouTube"、按 Enter；GPT-4 则做不到）。
